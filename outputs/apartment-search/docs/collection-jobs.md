# DB 수집 이력과 실패 재시도

V6의 collection_job은 실행 시도마다 UUID를 발급해 지역 코드·표시명·계약월·상태·시도 번호·건수·시간·실패 유형을 저장한다. 과거 실패 행을 덮어쓰지 않는다. 이전에 수집한 거래나 JSON 기록을 자동으로 소급 이관하지 않는다.

## 저장 및 복구 규칙

- RUNNING → SUCCEEDED / FAILED / INTERRUPTED. 빈 정상 응답도 saved=0으로 성공 기록한다.
- 시작 시 기존 molit_import_state의 전역 잠금을 사용해 같은 지역·월의 활성 작업을 검사한다. 다른 JVM에서도 동일 DB를 사용하는 한 중복 실행을 거부한다.
- 전체 API 페이지를 읽은 후 거래 스냅샷 교체와 SUCCEEDED 기록을 하나의 트랜잭션으로 커밋한다. 저장 실패 시 둘 다 롤백한다. 실패 이력은 별도 트랜잭션으로 남긴다.
- 유효 시간은 DB 시계 기준 30분으로 고정하며 heartbeat 연장은 없다. 만료된 작업은 늦게 응답해도 거래를 저장할 수 없다. 30분을 넘는 수집은 완료로 처리되지 않으며 재시도가 필요하다.
- 애플리케이션 시작, 새 작업/재시도, 관리 API 조회 시 만료 RUNNING을 INTERRUPTED로 전환한다. 살아 있는 다른 인스턴스를 방해하지 않도록 재시작 직후 모든 RUNNING을 무조건 실패 처리하지 않는다.
- 실패/중단된 가장 최근 시도만 재시도할 수 있다. 이미 성공한 구간을 갱신하려면 새 작업을 생성한다. 자동 외부 API 재호출 스케줄은 추가하지 않았다.
- FETCH_FAILED: 인증·호출 한도·네트워크·응답 검증 등을 포함하는 수집 실패. STORE_FAILED: 저장 실패. EXECUTOR_BUSY: API 작업기 사용 중. LEASE_EXPIRED: 유효 시간 만료. 외부 URL·응답·인증키·예외 원문은 저장하지 않는다.
- 기존 CLI importer와 전국 수집 스크립트도 실제 새 이미지/코드로 실행하면 DB 이력을 기록한다. JSON 체크포인트는 실행 목록 건너뛰기에 계속 사용한다.

## 관리 API (기본 비활성화)

의도적으로 활성화한 로컬 개발 실행에서만 먼저 검증한다. IDE 실행 환경에 `COLLECTION_API_ENABLED=true`, 32자 이상 무작위 `COLLECTION_ADMIN_TOKEN`, `MOLIT_SERVICE_KEY`를 설정한다. 키는 채팅·Git·URL에 넣지 않는다. 기존 Compose 웹 서비스에는 API 키를 주입하지 않으므로 이 변경만으로 공개 서버에서 관리 API가 켜지지 않는다.

모든 요청은 `X-Collection-Token` 헤더가 필요하다. 활성화되었는데 토큰이 짧으면 시작 실패한다. 외부 공개 시 HTTPS가 필요하며 Caddy의 기존 공개 경로 정책도 별도 검토해야 한다. 이번 작업에는 AWS 활성화/배포가 포함되지 않는다.

| 메서드·경로 | 동작 |
| --- | --- |
| GET /api/admin/collection-jobs?limit=20 | 최근 목록, limit 1~100 |
| GET /api/admin/collection-jobs/{id} | 단일 상태 조회 |
| POST /api/admin/collection-jobs | 한 지역·월의 비동기 작업 시작, 202와 id 반환 |
| POST /api/admin/collection-jobs/{id}/retry | 실패/중단 작업 새 시도 생성 |

생성 JSON 예시(코드·표시명은 검증된 config/molit-regions.tsv 목록 사용):

```json
{"regionCode":"11110","province":"서울","district":"종로구","month":"202609"}
```

API 작업기는 인스턴스당 1개이며 메모리 대기열은 두지 않는다. 사용 중이면 실행 이력에 EXECUTOR_BUSY를 남기고 409를 반환한다. DB 목록에서 해당 작업을 확인할 수 있다. 인증 실패 401, 잘못된 입력 400, 없는 작업 404, 중복·재시도 조건 불충족 409, 미설정 API 키 503이다.

프로세스가 강제 종료되면 작업은 최대 30분 뒤 만료 대상으로 식별된다. 만료된 작업을 조회·재시도하는 과정은 명시적이며 자동 재실행을 보장하지 않는다. 작업 이력 페이지네이션·보존 기간 정책·heartbeat·관리 화면은 후속 범위다.

## 검증

외부 API 대신 모의 응답과 독립 H2/PostgreSQL 테스트 DB를 사용한다. 중복 요청, 실패 재시도와 이력 보존, 만료 후 오래된 작업의 저장 거부, 저장 실패 롤백, 기본 API 비활성화, 인증·입력 검증, 비동기 실패 후 성공 재시도, CLI 수집기의 이력 연결, PostgreSQL 동시 시작을 검증한다. 구현 전 테스트는 클래스 미존재로 컴파일 실패를 확인했으며, 완성된 구현에 대한 모든 테스트 결과는 PR에 기록한다.

## 관리자 웹 화면

`/admin`에서 토큰 연결, 최근 100개 작업의 상태별 집계·필터, 새 지역/월 수집, 최신 실패·중단 작업 재시도를 제공한다. 집계는 전체 거래 수가 아닌 조회된 작업 기준이며 자동 polling 없이 새로고침 버튼으로 갱신한다.

IntelliJ 실행 환경 변수에 `COLLECTION_API_ENABLED=true`, `COLLECTION_ADMIN_TOKEN`(임의의 32자 이상 토큰)을 설정하고 앱을 재시작한다. 조회만 할 때는 공공 API 키가 없어도 된다. 수집·재시도에는 기존 `MOLIT_SERVICE_KEY`가 필요하다. 앱 포트가 8081이면 `http://localhost:8081/admin`으로 접속한다. Docker는 해당 환경 변수들을 앱 컨테이너에 명시적으로 전달해야 하며 `.env`에만 적어서는 전달되지 않는다. 운영에서는 HTTPS로 접속한다.

기본 비활성화일 때 화면과 API 모두 404. 활성화된 화면은 데이터가 없는 공개 셸이며 실제 조회·변경은 기존 토큰 인증 API를 사용한다. 토큰은 URL·쿠키·localStorage에 저장하지 않고 현재 탭의 메모리에서만 유지하며 새로고침/연결 해제로 지운다. 사용자 계정/세션 로그인은 아니다. 페이지 응답은 no-store이며 데이터를 HTML에 삽입하지 않고 textContent로 렌더링한다.

지역 코드·시도·시군구는 `config/molit-regions.tsv` 기준으로 입력한다. 버튼 클릭 후 확인해야 수집을 요청하며 중복 클릭을 막는다. 최신 시도 여부는 서버에서도 다시 검사한다. 기존 저장 정책·마이그레이션은 변경하지 않는다.

검증: 화면 활성화 테스트에서 구현 전 404 실패 확인 → 구현 후 통과. 기본 비활성화 테스트 추가. `clean verify -Ppostgres-it`: 기본 54개 + PostgreSQL 12개 통과. 브라우저에서 검증용 토큰 연결 및 빈 이력 화면 확인. 실제 공공 API 수집/운영 배포는 수행하지 않음.

## 지역·월별 데이터 현황

관리자 화면에서 지역 코드와 시작/종료 계약월(최대 12개월)을 입력한다. `GET /api/admin/collection-jobs/coverage?regionCode=11110&from=202601&to=202609`는 기존 관리 토큰을 요구하며 공공 API를 호출하지 않는다. 공식 지역 코드 목록을 기준으로 입력한다. 현 단계는 지역 한 곳씩 조회하며 전국 매트릭스/지역 선택 목록은 제공하지 않는다.

- 저장 건수: 해당 지역·계약월의 MOLIT 거래 수. 최근 100개 작업 제한과 무관하다.
- 미수집: 거래와 작업 이력이 모두 없음. 이력 도입 전 0건 수집 여부는 복원할 수 없다.
- 데이터 있음·이력 없음: 기존 거래가 있으나 작업 이력 없음. 성공 시각을 추정하지 않는다.
- 수집 성공·0건: 최신 시도가 성공이며 현재 거래 0건. 해제 거래만 있었던 경우도 포함한다.
- 실패/중단/실행 중: 최신 시도 상태. 이전 성공 데이터가 남을 수 있으므로 건수와 함께 확인한다.
- 마지막 성공: 해당 구간의 가장 최근 SUCCEEDED finished_at. 일반 DB 수정 시각이 아니며 이력이 없으면 확인 불가.

집계 두 쿼리는 REPEATABLE_READ 읽기 트랜잭션으로 같은 스냅샷을 사용한다. 값은 바인딩하며 구간별 반복 조회 대신 범위 집계와 윈도 함수로 최신 시도를 가져온다. 스키마 변경 없음. 화면은 조회 시점 결과이며 수집 후 현황 조회를 다시 누른다. 수집 준비 버튼은 지역 코드·계약월만 채우고 자동으로 수집하지 않는다. 시도·시군구를 확인하고 별도 요청한다.

검증(2026-11-03): 추가 테스트 5개(미수집/0건 성공, 기존 이력 없는 데이터·지역 격리, 최신 실패/이전 성공, 인증·기간 제한, PostgreSQL 집계). API 테스트 4개의 구현 전 404 실패 확인 후 구현. 최종 verify -Ppostgres-it 기본 58개 + PostgreSQL 13개 통과. 브라우저에서 2개월 미수집 조회 및 수집 준비 입력 연결 확인. 실제 수집·AWS 배포 없음.

## 실패 사례 모음

관리자 화면에 실패·중단 이력을 별도로 모은다. `GET /api/admin/collection-jobs/failures?limit=100`은 기존 관리 토큰을 요구하며 FAILED/INTERRUPTED만 먼저 필터링해 최근 100개까지 반환한다. 최근 전체 작업 100개에 포함되지 않는 과거 실패도 표시한다. 발생 시각 내림차순이며 이후 성공한 작업의 과거 실패도 삭제하지 않는다.

지역·계약월·시도·오류 분류·발생 시각·점검 안내를 표시하고 4개 실패 유형별로 필터링한다. 점검 가이드는 가능한 확인 사항이며 원인 확정 진단이 아니다. 원문 오류/공공 API URL/키는 표시하지 않는다. 해당 지역·월에 더 높은 시도가 있으면 재시도 버튼을 숨기며 실제 재시도 요청에서도 기존 서버 검증을 유지한다. 목록 갱신은 연결·새로고침·재시도 후 이루어진다. 목록이 없으면 실제 이력 없음 안내를 표시하며 예시 실패 데이터를 삽입하지 않는다.

2026-11-03 검증: 추가 4개 테스트(인증·한도·빈 목록, 성공 101건 이후에도 과거 실패 조회, 만료 복구/최신 재시도 판정, PostgreSQL 실패 집계). API 테스트 구현 전 404 실패 확인. clean verify -Ppostgres-it 기본 61개 + PostgreSQL 14개 통과. JS 구문 및 브라우저 빈 목록·유형별 점검 가이드 확인. 실제 수집·AWS 배포 없음.
